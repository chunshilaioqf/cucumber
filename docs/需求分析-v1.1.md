## 1. 项目概述

### 1.1 产品定位

构建一款轻量级、跨平台的**本地进程与服务统一管理工具**。用户既可以通过**配置命令**的方式管理自定义进程（启动、停止、检查、依赖安装），也可以让工具**直接调用系统级进程管理能力**，在不侵入目标进程生命周期的前提下进行观察与基础控制。工具同时暴露**本地 API、WebSocket 与 MCP 接口**，使 AI Agent 和外部脚本能够以编程方式操作本工具管理的全部进程与服务。

### 1.2 框架选型前提

本项目基于 **wind-ui-rust** 开发。命令式 Builder 风格的 retained-mode 跨平台 GUI 库，Windows 使用 Win32（+DirectWrite），macOS 使用 Cocoa/AppKit（+CoreText），Linux 使用 X11（x11rb），原生 Wayland 需通过 `WINDUI_BACKEND=wayland` 手动启用，默认经 XWayland 运行。控件树、布局、事件与主题全平台无关。

**约束**：凡是 wind-ui-rust 原生不提供的系统级能力（系统托盘、原生文件对话框、浏览器调用等），都需要在设计中显式标注为"需引入第三方 crate 或自行实现平台层代码"，不能假定框架自带。

### 1.3 核心设计原则

- **配置驱动优先**：进程的启动、停止、检查、依赖安装均由用户配置的命令模板驱动，不强制要求目标进程具备特定的服务协议。
- **观察与控制分离**：系统级进程管理（枚举、PID、资源）只做"观察 + 基础信号控制"；需要复杂生命周期的进程走"配置命令"路径。
- **AI 可操作性作为一等公民**：API / WS / MCP 接口与 GUI 功能对等，skill 安装降低 AI 接入门槛。
- **轻量优先**：沿用 wind-ui-rust 的低内存、空闲零 CPU 特性，避免为日志查看等功能引入重量级依赖。

## 4. 技术架构建议（原文要点）

分层 `ui/ core/ api/ platform/`；选型 windui + sysinfo + std/tokio process + axum/tokio + 自研日志解析 + skill 目录约定自实现 + 浏览器打开平台层 Command。

## 5. 风险与边界（原文索引）

- **R-01** wind-ui-rust 社区支持有限 → UI 适配层 + 原型验证（已完成）。
- **R-02** 日志高亮最不确定 → 先"行级着色 + 单关键词"（已落地）。
- **R-03** 系统级服务管理语义边界 → v1 限定观察 + 基础信号控制。
- **R-04** MCP SDK 版本兼容 → 采用自研 JSON-RPC 子集（ADR-01，零依赖）。
- **R-05** 跨平台停止信号差异 → stop_command 首选，信号尽力而为。
- **R-06** 跨平台构建不能交叉编译 → CI 原生 runner 矩阵。

## 6. 实施顺序（原文）

阶段一（核心闭环）→ 阶段二（日志查看）→ 阶段三（服务与接口）→ 阶段四（文档与打磨）。
> **实现说明**：0.1.0 已完成全部四个阶段的 v1 范围。

## 7. 构建与发布（原文要点）

- 原生 runner 矩阵：windows-latest（x86_64-msvc）、macos-14（aarch64 + x86_64 → lipo universal）、ubuntu-22.04（glibc 基线）。
- `ci.yml`（fmt/clippy/测试/编译 + Linux Xvfb 冒烟）与 `release.yml`（tag 触发、三平台产物、SHA256SUMS、tag 与 Cargo.toml 版本一致性校验、预发布自动标记）。
- UI 冒烟：Linux `xvfb-run` + `--smoke-test` 自动退出；Windows/macOS 仅编译验证。
- 产物命名 `<bin>-<version>-<platform>.zip|.tar.gz`；版本信息 build.rs 注入。
- 签名（可选后续）：macOS Developer ID + 公证；Windows EV/OV 证书。

**结论（原文）**：这份需求在 wind-ui-rust 上整体可行，但可行性是**有边界的**——建议严格按阶段推进，每个阶段结束时做框架层面的"压力验证"；CI 流水线应在阶段一结束时即建立，保证三平台编译始终可用。
